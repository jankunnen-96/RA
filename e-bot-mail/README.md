# e-bot-mail

Standalone bot that monitors an IMAP inbox for trigger emails from deimmowinkel.be and automatically follows the action links inside them (e.g. "bekijk aanvraag", "accepteren"), including fully completing the approval for "accepteren" requests. Controlled via a simple HTTP API with activate/deactivate endpoints, which an iPhone Shortcut calls remotely.

---

## How it works

A single script (`bot.py`) runs two things simultaneously:

**HTTP server (always on)** — listens on port 8001. Manages a flag file (`e-bot-mail/active`) that acts as an on/off switch. The API is the only way to flip this switch.

**Email monitor loop (always on)** — polls the IMAP inbox every 5 seconds. When the flag is on, it connects to the inbox, finds new trigger emails, extracts links, follows them, and logs the result to `e-bot-mail/logs/`. When the flag is off, it does nothing and waits for the next poll.

The bot stays running permanently. You control its behavior via the API. The poll interval is deliberately short (`POLL_INTERVAL` in `bot.py`) because the bot is racing to accept inspection requests before other agents do.

### Tracking which emails are new

The bot does **not** rely on the IMAP "unseen" flag to decide which emails are new. That flag is shared across every mail client connected to the inbox (webmail, phone apps, etc.), and any of them can mark an email as read before the bot ever sees it — which would cause the bot to silently skip it.

Instead, the bot tracks its own progress using IMAP UIDs (a permanent, ever-increasing ID per email) stored in `e-bot-mail/last_uid.txt`. Each cycle it looks at all emails from the trigger sender with a UID higher than the last one it processed, handles each one that matches the trigger subject, and advances the stored UID — regardless of read/unread state. This also means a single irrelevant email from the sender can no longer block newer relevant ones behind it (the old design got stuck reprocessing the same email forever if its subject didn't match).

On first run (no `last_uid.txt` yet), the bot seeds itself to the current newest email and does not process the historical backlog.

### "accepteren" links: full automated approval

"Bekijk aanvraag" links are simple GET requests, logged as-is.

"accepteren" links require actually completing the approval, which involves three steps handled automatically:

1. **Login.** The link redirects to `dashboard.deimmowinkel.be/user/login`. The bot logs in using `ACCOUNT_EMAIL` / `ACCOUNT_PASSWORD`.
2. **Destination re-fetch.** The Drupal login form doesn't always redirect to the original destination page after a successful login (it can land on the generic dashboard homepage instead). The bot explicitly re-requests the destination URL with the now-authenticated session to force navigation to the actual approval page.
3. **Antibot bypass.** The approval page contains a confirmation form protected by Drupal's [Antibot module](https://www.drupal.org/project/antibot), which normally requires real browser JavaScript (triggered by a mousemove/touch/keydown event) before it reveals the true form action and a computed `antibot_key` value. That key is generated by a purely deterministic client-side transform (reverse the key, split into 2-character chunks, reverse each chunk, join them back together) — see `compute_antibot_key()` in `bot.py`. The bot replicates this transform server-side and submits the form directly to its real `data-action` URL, completing the approval without a browser.

The full final page (after login, destination re-fetch, and form submission) is saved to `e-bot-mail/logs/TIMESTAMP_accepteren.html` for verification.

If the "accepteren" flow completes with a `200` response and no error, the bot sends a notification email (via SMTP, same mailbox credentials) to `NOTIFY_EMAIL` with the request subject and a link to the case page, so a human can double-check the outcome.

## Deployment

- **Server:** Bluehost VPS at `129.121.109.129`
- **Repo path on server:** `/opt/matchadaddy/RA/`
- **External URL:** `https://api.matchadaddy.uk/bot/...`

## Environment variables

Stored in `/opt/matchadaddy/RA/.env` on the server. Use `.env.example` in the repo root as a template.

| Variable | Required | Default | Description |
|---|---|---|---|
| `BOT_TOKEN` | Yes | — | Secret token required to call activate/deactivate |
| `BOT_PORT` | No | `8001` | Port the server listens on |
| `EMAIL_ADDRESS` | Yes | — | IMAP login email address |
| `EMAIL_PASSWORD` | Yes | — | IMAP login password |
| `EMAIL_IMAP_SERVER` | No | `webreus.email` | IMAP server hostname |
| `EMAIL_SMTP_SERVER` | No | same as `EMAIL_IMAP_SERVER` | SMTP server hostname, used to send acceptance notifications |
| `EMAIL_SMTP_PORT` | No | `587` | SMTP port (STARTTLS) |
| `NOTIFY_EMAIL` | No | `info@epb-philips.be` | Address that receives a notification when a request is successfully accepted |
| `ACCOUNT_EMAIL` | Yes | — | dashboard.deimmowinkel.be login email, used to complete "accepteren" approvals |
| `ACCOUNT_PASSWORD` | Yes | — | dashboard.deimmowinkel.be login password |

## API endpoints

All endpoints are available externally via `https://api.matchadaddy.uk`.

### GET `/bot/status`
Returns whether the bot is currently active (flag file exists).

```
GET /bot/status
→ {"active": true}
```

### POST `/bot/activate?token=TOKEN`
Turns on email processing.

```
POST /bot/activate?token=YOUR_TOKEN
→ {"status": "activated"}
```

### POST `/bot/deactivate?token=TOKEN`
Turns off email processing.

```
POST /bot/deactivate?token=YOUR_TOKEN
→ {"status": "deactivated"}
```

Returns `403` if the token is missing or wrong.

## Systemd service

`bot.py` runs as a systemd service so it starts automatically at boot and restarts if it crashes.

**Install the service (first time only):**
```bash
cp /opt/matchadaddy/RA/e-bot-mail/e-bot-mail.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable e-bot-mail
systemctl start e-bot-mail
```

**Common commands:**
```bash
systemctl status e-bot-mail      # check if running
systemctl restart e-bot-mail     # restart after code changes
systemctl stop e-bot-mail        # stop the bot
journalctl -u e-bot-mail -f      # live logs
```

**After pulling new code**, always restart the service to pick up changes:
```bash
git pull && systemctl restart e-bot-mail
```

## iPhone Shortcut

Shortcuts named "activeer" and "deactiveer" call `/bot/activate` and `/bot/deactivate` via POST requests with the token as a query parameter. They use the Dutch iOS Shortcuts action "Haal inhoud van URL" with method set to POST.

## Nightly git pull (cron)

A cron job pulls the latest code and CSV files from GitHub every night at 1:00 AM GMT:

```
0 1 * * * cd /opt/matchadaddy/RA && git pull >> /var/log/ra-pull.log 2>&1
```

After a pull that includes Python code changes, restart the service:
```bash
systemctl restart e-bot-mail
```

CSV file updates do not require a restart.

## Trigger configuration

Defined as constants in `bot.py`:

| Constant | Value |
|---|---|
| `TRIGGER_SENDER` | `noreply@deimmowinkel.be` |
| `TRIGGER_SUBJECT` | `Nieuwe keuringsaanvraag` |
| `target_keywords` | `bekijk aanvraag`, `accepteren` |
| `POLL_INTERVAL` | `5` (seconds) |

Only new emails (by UID, see above) matching both sender and subject are processed. Only links whose text contains one of the target keywords are followed.
